# Allo

A cross-platform chat app built with Expo, React Native, and a Node.js /
Express backend. Every conversation, direct or group, is one MLS group
(RFC 9420); every installation is its own cryptographic instance; the server
stores and relays ciphertext and never holds a key that opens it.

## What it is

Allo is the Oxy ecosystem's encrypted messenger, and the messaging platform
other Oxy apps will consume. The frontend is an Expo Router app that targets
iOS, Android, and Web from one codebase and gets everything chat from the
`@allo/react` hooks over the headless `@allo/core` SDK. The backend is an
Express service over Postgres that brokers instances, key packages,
conversations, encrypted events, delivery, sync and media, plus Socket.IO for
nudges.

Identity is delegated to the Oxy platform: users sign in with their Oxy
account through `@oxy.so/services`, the backend trusts the resulting token,
and there is no separate user database in Allo. What the server holds per
account is its instances and their public keys, conversation membership,
ciphertext events, delivery state, blobs, and a small settings document.

For account management UI see [MyAccount](/developers/docs/accounts). For the
underlying RN SDK see [@oxy.so/services](/developers/docs/services).

## Architecture

```
   Allo frontend (Expo / RN / web)
     @allo/react  ->  @allo/core  ---- REST /v1, signed per instance ---->  Allo backend
                        |            <--- Socket.IO /v1: nudges, typing ---  (Express + Postgres)
                        v                                                        |
     encrypted local store (SQLite / IndexedDB)                                   v
     secret store (Keychain / Keystore / IndexedDB)                    Postgres: ciphertext events,
       instance key, storage key                                       instances, deliveries, blobs
                                                                       + Oxy API (auth, profiles)
```

The split is strict: a message is plaintext only inside the sending and
receiving instances. Group names, read receipts, reactions and typing are
encrypted application messages too.

Inside `packages/`:

| Package | Role |
| --- | --- |
| `shared-types` (`@allo/shared-types`) | The v1 wire contract as zod schemas and types. Built first. |
| `core` (`@allo/core`) | The headless SDK: MLS through `CryptoEngine`, the instance model, encrypted storage, sync, outbox, conversations, messages, media. No React. |
| `react` (`@allo/react`) | `AlloProvider` and hooks over the client. Plain React. |
| `frontend` (`@allo/frontend`) | The Expo app. Consumes `@allo/react` for chat and carries no engine code. |
| `backend` (`@allo/backend`) | Express + drizzle + Socket.IO. A modular monolith over Postgres. |

Build order: `shared-types`, then `core`, then `react` (all three by
`postinstall`), then `frontend` and `backend`.

## Threat model

The full model, with assets, actors, what MLS gives, what the instance model
gives, what the server can still see and what is not defended, is
[Threat model](./platform/threat-model). In short:

- **What the server sees:** who talks to whom, when, how much, which
  installations hold a leaf, ciphertext sizes, blob sizes, presence, push
  tokens.
- **What the server cannot see:** any message, name, receipt, reaction or
  media file. It never holds a key.
- **What a stolen Oxy token cannot do:** act inside a conversation, because
  every such request is signed by the instance's private key, and a new
  instance it registers is pending until an existing device approves it.
- **Recovery:** there is no server-side reset. A new instance sees a
  conversation from the epoch it joined; history transfer and backup are not
  built yet, so losing every instance loses history.

## Install

Clone the repo and install with bun:

```sh
git clone https://github.com/OxyHQ/Allo.git
cd Allo
bun install
```

`bun install` resolves the workspaces, then `postinstall` builds
`@allo/shared-types`, `@allo/core` and `@allo/react` so the other packages can
type-check immediately.

### Prerequisites

- Node.js 20.19+ and Bun 1.3+
- PostgreSQL (local or hosted): the connection string goes into `packages/backend/.env`. `packages/backend/docker-compose.postgres.yml` brings up a local one.
- For iOS: macOS + Xcode. For Android: Android Studio.

### Environment

`packages/backend/.env`:

```env
# REQUIRED: the server refuses to boot without it.
DATABASE_URL=postgres://allo:allo@127.0.0.1:5440/allo_dev
# Read by @oxy.so/core, not by this package. Defaults to https://api.oxy.so.
OXY_API_URL=https://api.oxy.so
# 4140 is Allo's slot in the Oxy per-app port map; ECS injects PORT=8080.
PORT=4140
NODE_ENV=development
```

The full list (Redis for the Socket.IO adapter, the blob size cap, the push
providers, CrowdSource) is in the
[backend README](https://github.com/OxyHQ/Allo/blob/main/packages/backend/README.md#environment-configuration).
There is no `FRONTEND_URL` and no `JWT_SECRET`; the CORS allowlist is a
literal in `src/app.ts` plus whatever `createOxyCors` admits automatically.

`packages/frontend/.env` is optional. `config.ts` hardcodes production and
defaults development to `localhost:4140`, so a local run needs nothing set:

```env
API_URL=http://localhost:4140/api
API_URL_SOCKET=ws://localhost:4140
EXPO_PUBLIC_OXY_CLIENT_ID=your_oxy_client_id
```

See the [frontend README](https://github.com/OxyHQ/Allo/blob/main/packages/frontend/README.md#environment-setup)
for the full list.

## Quick start

Apply the schema once before the first run: a fresh database has no tables.

```sh
cd packages/backend
docker compose -f docker-compose.postgres.yml up -d   # if you have no Postgres
bun run db:migrate -- --target-database=allo_dev --phase=all
```

`--target-database` is mandatory and is checked against the database
`DATABASE_URL` actually points at, so a connection string left over from
another project cannot be migrated by accident. `--phase=all` is right for a
local database; the deploy runs `pre` and `post` around the rollout instead.

```sh
# Start everything (frontend + backend)
bun run dev

# Or one at a time
bun run dev:backend
bun run dev:frontend
```

Then in the Expo CLI, press `w` for web, `i` for iOS simulator, or `a` for
Android emulator.

## Core concepts

The vocabulary (Conversation, AppSpace, ClientInstance, enrollment, history
versus live state, media, push, storage rules, the connector boundary) is
[Concepts](./platform/concepts). The three ideas a newcomer needs:

### Instances, not devices

Every installation registers as a client instance with its own Ed25519 key.
The first instance on an account is active at once; every later one is
pending until an existing active instance approves it by signing a
server-issued challenge whose fingerprint the user compares on both screens.
There is no primary phone: a laptop is approved by a phone, or a phone by a
laptop. Revoking an instance refuses its signature, cuts its sockets, and has
a remaining instance commit its removal from every group.

### One conversation, one MLS group

A DM or a group is one MLS group whose leaves are the members' active
instances. Adding a member means claiming a key package for each of their
instances and committing an Add; the server stores the commit and the
welcome, advances the epoch, and fans the ciphertext out to every leaf. The
SDK adds an account's own new instances to its conversations by itself, and
removes revoked ones. Sending a message is encrypting an application message
to the group and posting it with an idempotency key; the durable outbox
retries until the server accepts it, and a stale epoch makes the client
re-sync and re-encrypt.

### Nudge, then pull

The server writes one delivery row per event and recipient instance in the
same transaction as the event, then nudges connected instances over the
socket. A client pulls `GET /v1/sync` from its persisted cursor, decrypts each
delivery through the engine, persists the result and the cursor in one
batch, and acks. A push notification says only "New message" and is a nudge
for an instance with no socket; the sync cursor is the truth.

### Routing

Frontend routing follows Expo Router conventions:

```
app/
  _layout.tsx
  (auth)/
    index.tsx            # sign-in
  (chat)/
    _layout.tsx          # two-pane at >=768px, plus a details column at >=1024px
    index.tsx            # conversation list
    new.tsx              # start a conversation
    c/[id].tsx           # individual conversation
    [username].tsx       # /@handle profile
    settings/...
  calls.tsx              # calls screen (mock data)
```

Mobile gets a single-pane stack. Tablet gets list + thread. Desktop adds a
contact-details column. All three come out of the single `(chat)/_layout.tsx`.
