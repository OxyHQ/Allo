# API

The Allo backend is an Express + Socket.IO service. It has two HTTP surfaces
behind Oxy authentication (`createOxyAuthMiddleware` from `@oxy.so/core/server`,
so every request carries `Authorization: Bearer <oxy access token>`): the
messaging platform under `/v1`, and the account-side routes under `/api`. The
middleware populates the account id from the token; the backend keys its own
records by that Oxy user id and never owns a user record itself.

Public routes: `GET /health/live`, `GET /health/ready` and its alias
`GET /api/health`. `POST /webhooks/crowdsource` sits outside both surfaces and
authenticates by signature.

## Base URL

| Env | URL |
| --- | --- |
| Production | `https://api.allo.you` |
| Development | `http://localhost:4140` |

Both are hardcoded in `packages/frontend/config.ts`; only the development
side can be overridden from the environment.

## Health

- `GET /health/live`: always 200 `{ status: "alive" }`. A draining task is still alive.
- `GET /health/ready`: 200 once the process has booted, verified the migration ledger (production) and can `select 1` against Postgres; 503 otherwise, with `phase` and `dependencies: { postgres, migrations }`. Drops to 503 on the first SIGTERM.
- `GET /api/health`: an alias of ready, kept for the existing load-balancer target group.

## Messaging platform: `/v1`

The route-by-route contract, the error codes, the request signing algorithm
and every socket event are in [API v1](./platform/api-v1); every request and
response shape is a zod schema in `@allo/shared-types`, and the backend
validates with the same schemas the SDK parses with. This page only orients.

| Area | Routes | Auth |
| --- | --- | --- |
| Instances | `POST/GET /v1/instances`, `GET /v1/accounts/:accountId/instances` | Oxy |
| Enrollment | `GET /v1/instances/pending`, `POST /v1/instances/:id/{approve,reject,revoke}`, `PUT/DELETE /v1/instances/me/push` | instance-signed |
| Key packages | `PUT /v1/key-packages`, `POST /v1/key-packages/claim` | instance-signed |
| Conversations | `POST/GET /v1/conversations`, `GET /v1/conversations/:id`, `POST /v1/conversations/:id/leave` | instance-signed |
| Events | `POST/GET /v1/conversations/:id/events` | instance-signed |
| Sync | `GET /v1/sync`, `POST /v1/sync/ack` | instance-signed |
| Blobs | `POST /v1/blobs` (raw octet-stream), `GET /v1/blobs/:id` | instance-signed |

"Instance-signed" means the Oxy bearer plus `X-Allo-Instance`,
`X-Allo-Timestamp` and `X-Allo-Signature`: an Ed25519 signature by the
installation's key over the method, the request target, the timestamp and the
SHA-256 of the raw body. A stolen Oxy token alone can call only the three
Oxy-only routes.

Every event payload is MLS ciphertext the server cannot read. Message text,
edits, deletions, reactions, read receipts, typing and group names are all
inside it; there is no route that accepts or returns plaintext, and
`__tests__/platform/noPlaintextPaths.test.ts` scans the routers to keep it
that way. Every non-2xx answer on `/v1` is `{ error: { code, message, details? } }`.

## Account-side routes: `/api`

### People directory

`GET /api/directory/*` answers the five Oxy lookups the app makes, so the app
draws a person through this backend rather than by calling Oxy itself:
profile by username, user by id, users by ids, profile search, asset URL.
Every answer is a `DirectoryUser` projection (id, handle, display name,
avatar, bio) rather than the Oxy `User`, which carries email, phone, address
and birthday. The [backend README](https://github.com/OxyHQ/Allo/blob/main/packages/backend/README.md#people-directory)
has the route table.

### Profile settings

Per-account settings document. There is no separate user record; these
settings hang off the Oxy user id.

- `GET /api/profile/settings/me`: the calling user's `UserSettings`.
- `GET /api/profile/settings/:userId`: another user's public-facing settings, subject to their privacy flags.
- `PUT /api/profile/settings`: patch. Top-level keys are merged; nested objects are deep-merged.

```jsonc
{
  "appearance": {
    "themeMode": "light" | "dark" | "system",
    "primaryColor": "#000000"
  },
  "profileHeaderImage": "https://...",
  "privacy": {
    "profileVisibility": "public" | "private" | "followers_only",
    "showContactInfo": true,
    "allowTags": true,
    "showOnlineStatus": true,
    "hideLikeCounts": false,
    "hideShareCounts": false,
    "hideReplyCounts": false,
    "hideSaveCounts": false,
    "hiddenWords": ["spoiler"],
    "restrictedUsers": ["userId"]
  },
  "profileCustomization": {
    "coverPhotoEnabled": true,
    "minimalistMode": false,
    "displayName": "Display Name",
    "coverImage": "https://..."
  }
}
```

- `DELETE /api/profile/settings/behavior`: reset learned UX preferences.

### Blocks and restricts

| Method | Path | Body |
| --- | --- | --- |
| `GET` | `/api/profile/blocks` | |
| `POST` | `/api/profile/blocks` | `{ blockedId }` |
| `DELETE` | `/api/profile/blocks/:blockedId` | |
| `GET` | `/api/profile/restricts` | |
| `POST` | `/api/profile/restricts` | `{ restrictedId }` |
| `DELETE` | `/api/profile/restricts/:restrictedId` | |

Both lists are written and stored; nothing in the messaging platform reads
them yet.

### Reports

Moderation intake, backed by CrowdSource. **Accounts only**: message content
is never submitted for review, because it is end-to-end encrypted and the
server never holds a key. The rule is enforced by the type of a subject
provider, by a test pinning `deliverableTypes()` to exactly `['user']`, and
by a test pinning the module graph a provider can reach.

- `POST /api/reports`: file a report against an account. `reportedId` is an Oxy account id; an `@handle` is accepted and stored with the reason it cannot be reviewed, and never delivered. Returns the created report.
- `GET /api/reports/mine`: the reports the calling user has filed.
- `POST /webhooks/crowdsource`: inbound decisions. Public but signature-verified, mounted only when `CROWDSOURCE_WEBHOOK_SECRET` is set, and registered ahead of the JSON body parser so the raw body survives for verification.

## Real-time (Socket.IO)

Namespace `/v1` on the same HTTP server. The handshake carries the Oxy bearer
and, in `handshake.auth`, the same three instance fields as a signed request,
with the path fixed to `/socket` and an empty body. A connected socket joins
`instance:<id>` and `account:<accountId>`.

| Event | Direction | Meaning |
| --- | --- | --- |
| `sync.nudge` | server to client | something is waiting in this instance's stream; pull `GET /v1/sync` |
| `instance.approved` | server to client | this instance is now active |
| `instance.revoked` | server to client (account room) | an instance of the account was revoked |
| `keypackages.low` | server to client | upload more key packages |
| `presence` | server to client | `{ accountId, online }`, best effort, for accounts sharing a conversation |
| `typing` | both ways | `{ conversationId, ciphertext }`: an MLS application message relayed to the conversation's other active leaves and never stored |

No message content travels over the socket. Payload schemas are in
`@allo/shared-types` (`sync.ts`).

## Errors

On `/v1`, every non-2xx answer is `{ error: { code, message, details? } }` and
the codes (`unauthorized`, `forbidden`, `not_found`, `validation_failed`,
`epoch_conflict`, `instance_not_active`, `instance_revoked`,
`key_packages_exhausted`, `idempotency_conflict`, `payload_too_large`,
`rate_limited`, `unavailable`, `internal`) with their HTTP statuses are
tabulated in [API v1](./platform/api-v1#errors). The `/api` routes answer
Oxy's own envelope. `429` comes from `createOxyRateLimit`, applied per
resolved user, on both surfaces.

## Schemas

Every table is drizzle, in `packages/backend/src/db/schema/`, one file per
domain, with `CONVENTIONS.md` binding. The messaging tables are
`client_instances`, `key_packages`, `conversations`, `conversation_members`,
`conversation_leaves`, `conversation_events`, `instance_deliveries`, `blobs`
and `blob_bytes`; the kept ones are `user_settings`, `blocks`, `restricts`,
`user_behavior` and the moderation tables. One line on each is in
[Architecture](./architecture#data-model).

TypeScript shapes for every `/v1` request and response are the zod schemas
in `@allo/shared-types`; `DirectoryUser` and the `/api` envelope live there
too.
