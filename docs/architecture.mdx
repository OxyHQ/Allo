# Architecture

Allo is a Bun workspace monorepo with five packages. The messaging engine is
an SDK the app consumes, not code inside the app; the backend is a modular
monolith over Postgres that stores and relays ciphertext. The decision behind
this shape is [ADR 0001](./adr/0001-clean-break-platform); the vocabulary is
[Concepts](./platform/concepts).

## Packages

```
packages/
  shared-types/   @allo/shared-types   the v1 wire contract: zod schemas and their types
  core/           @allo/core           headless messaging SDK (MLS, instances, sync, outbox, storage)
  react/          @allo/react          AlloProvider and hooks over @allo/core
  frontend/       @allo/frontend       Expo Router app for iOS, Android and web
  backend/        @allo/backend        Express, drizzle, Socket.IO
```

```
@allo/shared-types  <--  @allo/core  <--  @allo/react  <--  @allo/frontend
                    <--  @allo/backend
```

`shared-types` has no internal dependency and no React. `core` imports
nothing from React, Expo or React Native and runs under Node, browsers and
Hermes. `react` is plain React with no React Native import, so Expo consumes
it on every platform. The frontend consumes `@allo/react` for everything chat
and carries no engine code of its own. The backend consumes `shared-types`
only: it validates every `/v1` body and query with the same schemas the SDK
parses answers with.

The root `postinstall` builds `shared-types`, `core` and `react` in that
order, so the other packages type-check right after `bun install`. The SDK is
documented in [SDK](./platform/sdk), the contract in [API v1](./platform/api-v1).

Root scripts:

```sh
bun run dev                # every workspace
bun run dev:frontend       # @allo/frontend only
bun run dev:backend        # @allo/backend only
bun run build              # every workspace
bun run typecheck          # backend then frontend, no emit
bun run test               # every workspace
```

A root `lint` script exists but only the frontend has a working lint setup.

External shared dependencies: `@oxy.so/core` (auth client and types; its
`/server` entry supplies the backend's auth, CORS and rate-limit middleware),
`@oxy.so/db` (column helpers, uuid v7, the migrator), `@oxy.so/services` (the
React Native session, frontend only), `@oxy.so/bloom` (UI, frontend only),
`@oxy.so/crowdsource*` (moderation, backend only).

## Frontend

`packages/frontend/` is an Expo Router app. Chat state comes from
`@allo/react` hooks over one `AlloClient`; the client is constructed with
three platform adapters (Oxy session, an encrypted-at-rest byte store, a
secret store) described in [SDK](./platform/sdk). `packages/frontend/lib/allo/`
is the only place the app constructs the client and holds those adapters;
every chat screen consumes `@allo/react` hooks, and a TypeScript-AST census
(`__tests__/allo/noLegacyChatPath.test.ts`) fails the build if any other
path talks to the engine.

Unchanged by the platform change: routing (`app/`), styling (NativeWind and
Bloom theme tokens through `useTheme()`), the responsive layout in
`app/(chat)/_layout.tsx`, i18n (`lib/i18n.ts`, flat bundles in `locales/`),
profiles at `/@handle`, and the appearance and privacy settings screens.

## Backend

`packages/backend/` is one Express app with a Socket.IO server on the same
HTTP server. The shape is Mention's: pure assembly, fail-fast boot,
migrations before readiness, transactional outbox, lease-claimed workers,
graceful shutdown, sanitised logs.

### Module map

```
server.ts                       bootstrap only: env, Postgres, migration ledger, sockets, workers, listen, ready
src/app.ts                      createApp(deps): pure HTTP assembly, middleware order, the one error handler
src/runtimeApp.ts               the concrete deps (Oxy client, CORS, rate limit, auth, routers)
src/runtime/                    health state, realtime seam, Socket.IO server, Redis adapter, shutdown, global handlers
src/middleware/                 instanceAuth (Ed25519 request signature), oxySession, requestObservability
src/routes/v1/                  one router per contract file: instances, keyPackages, conversations, events, sync, blobs, history, backups
src/routes/                     the kept /api routers: directory, profileSettings, reports, crowdSourceWebhook
src/services/platform/          the rules: instances, key packages, conversations, events and sync, blobs, history offers, backups, wire projections
src/db/schema/                  one file per domain; CONVENTIONS.md is binding
src/db/platform/                repositories; appendClientEvent is the event-log transaction
src/workers/                    deliveryWorker, blobGc
src/services/push/              FCM and APNs senders
src/services/moderation/        the CrowdSource pipeline
drizzle/                        generated migrations, one deploy-phase marker each
```

**Runtime.** `createApp(deps)` never listens, never opens Postgres, never
creates a Socket.IO server and never starts a timer; tests build fakes for
its deps. Middleware order is the contract: request observability, CORS,
health routes, the raw-body routes (`/webhooks` and `POST /v1/blobs`) ahead of
`express.json({ verify })` which stashes the raw body for the signature,
no-store headers, per-user rate limit, `/api` behind Oxy auth, `/v1` behind
Oxy auth with the instance signature per route, a JSON 404, and one error
handler that turns zod errors into `validation_failed`, `AlloHttpError` into
its code, body-parser's 413 into `payload_too_large`, and everything else into
`500 internal` with no message. `server.ts` boots in a fixed order and marks
the process ready last; `markRuntimeReady` throws if migrations were not
marked complete first. `GET /health/live` is always 200; `GET /health/ready`
(and its alias `GET /api/health`) is 200 only when the phase is ready,
migrations are verified and Postgres answers `select 1`. Shutdown drops
readiness first, stops workers while Postgres is still open, then closes
HTTP, sockets, the Redis adapter and the pool together, with a ten-second
deadline.

**Auth.** One way in: an Oxy bearer token, validated by `@oxy.so/core/server`
and naming the account. Every route that acts as one installation also
requires `X-Allo-Instance`, `X-Allo-Timestamp` and `X-Allo-Signature`, an
Ed25519 signature by the instance's key over the method, request target,
timestamp and raw-body digest (`middleware/instanceAuth.ts`). The three
Oxy-only routes are register, list own instances and list another account's
public instances. There is no user table; identity is Oxy's.

**Instances and key packages** (`services/platform/instanceService.ts`,
`keyPackageService.ts`): registration with the bootstrap rule, pending
enrollments, approval by signature, rejection, revocation (which marks
leaves removed, appends a control event, and disconnects sockets), push token
registration; key package upload with unique refs and one-time claims that
nudge an instance whose stock runs low.

**Conversations and events** (`conversationService.ts`, `eventService.ts`,
`db/platform/eventRepository.ts`): DM idempotency on `dm_key`, group
uniqueness on `mls_group_id`, the initial commit appended in the create
transaction; `appendClientEvent` runs under `SELECT ... FOR UPDATE` on the
conversation row and is where the epoch compare-and-set, the dense `seq`, the
add and remove authorization, the welcome's separate event, the membership
updates, the stored GroupInfo and the delivery rows are one write or none.
Every `mls_commit` carries the new epoch's GroupInfo, upserted into
`conversation_group_info` in the same transaction; a commit of `kind:
external` needs a `joined` member row rather than a leaf, must add exactly its
sender, and activates that leaf at once; `kind: resync` must add and remove
exactly its sender and replaces the leaf row. `GET /v1/conversations/:id/group-info`
returns the stored GroupInfo, or `null` when it is not the current epoch's, to
an instance whose account is a joined member; `PUT` lets an active leaf
re-publish one for the current epoch only (`409 epoch_conflict` otherwise),
which is how conversations older than the field become joinable. The server
never parses the bytes. Server-side leave writes a `member_left` control
event.

**Deliveries and sync** (`db/platform/deliveryRepository.ts`): one
`instance_deliveries` row per event and recipient, written in the event's
transaction; `GET /v1/sync` walks an instance's rows by integer id and the
cursor is that id in base64url; `POST /v1/sync/ack` marks everything up to it.

**Blobs** (`blobService.ts`, `db/platform/blobRepository.ts`): size cap
(`ALLO_BLOB_MAX_BYTES`, default 25 MiB), digest check, a 32-random-byte hex
id, bytes in `blob_bytes` behind a `BlobStore` interface so S3 can replace it.

**History offers and backups** (`historyService.ts`, `backupService.ts`,
`db/platform/historyRepository.ts`): the E2EE archive routes. An offer is
created only when the donor is active, the recipient is an active instance of
the same account with a transfer key (`transfer_key_missing` otherwise),
every chunk blob exists and belongs to the donor's account, and the manifest
signature verifies against the donor's key; one pending offer per donor and
recipient, a newer one expiring the older; `history.offer` to the recipient's
socket room after commit; a seven-day deadline; only the recipient lists or
consumes. A backup is one row per account, replaced whole, its signature
verified against the writing instance; `PUT /v1/instances/me/transfer-key`
publishes a key for an instance that predates the column. The server checks
signatures so garbage never reaches an inbox, and holds no key to anything.

**Workers.** All started after Postgres is verified, all stopped in the
drain before the pool closes, none leader-gated because every claim is
`FOR UPDATE SKIP LOCKED`. The delivery worker (every second, batch 100) claims
due deliveries under a lease and nudges a connected instance over the socket
or, for an `app_message` to an instance with a push token and no live socket,
sends "New message" with the conversation and event ids and nothing else; a
transient failure backs off, a rejected token is cleared, a revoked
instance's deliveries go dead. The expiry sweep (every minute) deletes rows
past `expires_at`: deliveries after 30 days, unreferenced blobs after 7 days,
moderation rows after 90, history offers 7 days after creation; before it
deletes anything it marks every pending offer past its deadline `expired` and
releases its chunks. Chunk retention is the repository's one rule: a blob
named by a pending offer or by the backup has `expires_at = null`, and when
that stops (consumed, expired, replaced, deleted) it is dated a day out
unless another pending offer, the backup or an event still names it. The
blob collector (hourly) adds the two cases the sweep cannot express:
unreferenced blobs of a revoked uploader, and an undated chunk older than
the offer lifetime that nothing names any more, which it dates rather than
deletes. The moderation outbox dispatcher is unchanged.

**Kept modules.** The people directory (`routes/directory.ts`, a projection
of Oxy profiles), profile settings and social (`routes/profileSettings.ts`,
`db/social/`), moderation (`services/moderation/`, account reports only,
`POST /api/reports`, the CrowdSource webhook), the push senders
(`services/push/`, FCM and APNs, the latter HTTP/2 with an ES256 provider
token and no library), and the ecosystem activity publisher.

### Data model

Schema is `src/db/schema/`, one file per domain; `CONVENTIONS.md` there is
binding (text ids, closed sets as CHECKs, `timestamptz`, no foreign keys to
Oxy ids). Column-level detail is in the schema files' comments.

| table | one line |
| --- | --- |
| `client_instances` | one row per installation: account, app, platform, raw Ed25519 public key (unique per account), status `pending`/`active`/`revoked`, the enrollment challenge, the approver and its signature, push provider and token (a protected column) |
| `key_packages` | an instance's published MLS key packages, opaque, unique by ref, consumed at most once; gone with the instance |
| `conversations` | kind `dm`/`group`, app, the unique `dm_key` for a DM, the unique MLS group id, `current_epoch` and `last_seq` advanced under the row lock |
| `conversation_members` | one row per (conversation, account): role `owner`/`admin`/`member`, state `joined`/`left`/`removed`; rows are kept as membership history |
| `conversation_leaves` | which instances hold a leaf: state `pending_welcome`/`active`/`removed`, the epoch added and the epoch removed |
| `conversation_group_info` | one row per conversation: the latest epoch's serialized MLS GroupInfo (`external_pub` plus ratchet tree, a protected column, at most 256 KiB), the epoch and the signing instance; written in the commit's transaction, read by a joined member's device to join by external commit |
| `conversation_events` | the append-only log: dense `seq` per conversation, kind, epoch, sender, idempotency key (unique per sender instance), `payload` as ciphertext bytes or server-authored control JSON, declared `blob_ids` |
| `instance_deliveries` | the outbox and the per-instance sync stream: a `bigserial` id (the one integer key, because it is the cursor), status, lease, attempts, expiry at 30 days |
| `blobs` / `blob_bytes` | uploaded ciphertext: size, digest, uploader, `expires_at` cleared when an event, a pending history offer or the account backup references it; the bytes in their own table behind `BlobStore` |
| `history_offers` | one donor instance's E2EE archive offered to another instance of the same account: the signed manifest (`jsonb`, validated on write, never queried inside), the HPKE-sealed archive key (a protected column), the donor's signature, the chunk blob ids as `text[]` for the retention queries, status `pending`/`consumed`/`expired`, `expires_at` seven days out |
| `account_backups` | one row per account, replaced whole: the writing instance, the signed manifest, the key check (a protected column; an HMAC the client compares before downloading), the chunk blob ids |
| `user_settings`, `blocks`, `restricts`, `user_behavior` | per-account settings and social lists, kept from before |
| `abuse_reports`, `moderation_events`, `moderation_outbox`, `moderation_enforcements` | the CrowdSource pipeline, kept from before |

Seven messaging columns are registered in `protectedColumns.ts` (beside the
two moderation payload columns) so a listing cannot serialise them by
accident: `client_instances.push_token`, `key_packages.data`,
`conversation_events.payload`, `conversation_group_info.data`,
`blob_bytes.data`, `history_offers.sealed_key` and
`account_backups.key_check`. The push token never leaves the process; the
readers that legitimately return the other six (the claim, the event and
sync reads, the group-info read for a joined member, the blob download, the
recipient's offer read and the owner's backup read) name them explicitly.

### Realtime

Socket.IO namespace `/v1` on the same HTTP server (`runtime/socket.ts`). Two
handshake middlewares in order: `oxy.authSocket()`, then the instance
signature over `handshake.auth` with the path fixed to `/socket` and an empty
body, through the same function the HTTP middleware uses. A connected socket
joins `instance:<id>` and `account:<accountId>`; the rooms are derived from
the verified instance, never from client input.

The pattern is nudge, then pull. Nothing of substance travels over the
socket: after an event's transaction commits, the server emits `sync.nudge`
to each recipient instance's room, and the client answers by pulling
`GET /v1/sync` from its persisted cursor. The nudge is the fast path and may
be lost; the delivery rows are the durable path, and the delivery worker
re-nudges or pushes whatever was not acked. The other server events are
`instance.approved`, `instance.revoked`, `keypackages.low`, `presence`
(best effort, to accounts sharing a conversation) and `history.offer` (to the
recipient instance's room; a nudge to list its offers, proving nothing by
itself). The one client event is `typing`, an MLS ciphertext relayed to the
conversation's other active leaves and stored nowhere.

With `REDIS_URL` set, the Redis adapter lets a room emit on one ECS task reach
a socket on another and lets the delivery worker ask whether an instance is
connected anywhere. Without it, or when Redis cannot be reached in five
seconds, the server runs single-instance and says so; Redis is not part of
readiness.

Domain code emits through the `Realtime` seam (`runtime/realtime.ts`); with
no server set, every call is a no-op, which is what tests and one-shot
scripts get.

## Build and deploy

| target | command | output |
| --- | --- | --- |
| Web | `bun run build:frontend` | `packages/frontend/dist/`, the static assets of the Cloudflare Worker `allo-frontend` (`packages/frontend/wrangler.toml`), deployed by `.github/workflows/deploy-frontends.yml`. `workers_dev = false` keeps `allo.you` the only hostname serving it. |
| iOS / Android | `eas build --platform ios` / `android` in `packages/frontend/` | EAS-managed `.ipa` / `.aab` |
| Backend | `bun run build:backend` | `packages/backend/dist/`, shipped as a `linux/arm64` image from `packages/backend/Dockerfile`, pushed to ECR as `oxy/allo` and rolled out on ECS by `.github/workflows/deploy-aws.yml`. Port `8080` injected by ECS (`4140` is the local default). Public URL `api.allo.you`. |

The deploy applies migrations in both phases: `--phase=pre` before the
rollout (additive, while the old image still serves) and `--phase=post` after
it (drops and narrowing). Every generated `.sql` carries exactly one
`-- oxy:deploy-phase=` marker, and a wrong marker is applied at the wrong side
of the rollout rather than merely mislabelled. `packages/backend/README.md`
has the migrator commands, the environment and the test setup.
