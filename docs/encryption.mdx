# Encryption

Allo encrypts every conversation, direct or group, as one MLS group
(RFC 9420). Each installation of the app is its own cryptographic instance
with its own Ed25519 key and its own leaf in every group it is in; the
backend stores and relays ciphertext and never holds a key that opens any of
it. This page says what runs and points at the pages that say how. The
static-ECDH design this replaced is described only in the ADR's "what is
replaced" table.

## What runs

**MLS, through `CryptoEngine`.** `@allo/core` wraps the `ts-mls` library
behind one interface (`packages/core/src/crypto/engine.ts`). Ciphersuite
`MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`; a leaf's credential names
`accountId:instanceId`; every key package an instance publishes is signed by
its long-lived instance key. Adds, removes and updates are commits that rotate
the group secret, so an instance that is removed holds nothing for the next
epoch. Text, edits, deletions, reactions, read receipts, typing and the
group's name are all application messages inside the group: the server sees
none of them. The crypto provider is pure JavaScript on every platform and
never calls `crypto.subtle`, because Hermes has no WebCrypto and one provider
means one key format. All of it, including the invariants the library does
not enforce and the SDK does, is [Allo Platform cryptography](./platform/crypto).

**The instance model.** The first instance on an account is active at once;
every later one is pending until an existing active instance signs its id,
its public key and a server-issued challenge, after the user has compared the
challenge's fingerprint. The approval and the challenge are published, so any
client verifies an account's whole approval chain from the listing before it
adds a leaf, and never on the server's word. Every request that touches a
conversation carries an Ed25519 signature over the method, path, timestamp
and body hash, so a stolen Oxy token alone cannot act inside one. Revoking an
instance refuses its signature, cuts its sockets, and has a remaining leaf
commit its removal. Sections 6 and 7 of the crypto page.

**Media.** A file is encrypted on the device with a fresh random key under
AES-256-GCM, uploaded as an opaque blob under an unguessable id, and the key,
nonce and digest travel only inside the encrypted `media` message. The server
checks size and digest and nothing else. Section 4 of the crypto page.

**Storage on the device.** Everything the SDK persists (group states, key
package private halves, decrypted timelines, the outbox, media keys) is
encrypted at rest with AES-256-GCM under a random storage key kept in the
platform secret store, namespaced by app, account and instance. Section 8 of
the crypto page.

What the server does and does not see, the actors it is designed against, and
the acceptance tests of the issue are in the
[threat model](./platform/threat-model).

## Known gaps

These are properties the engine does not yet have. Each has a place in the
[roadmap](./platform/roadmap).

- **No history transfer and no backup.** A new instance decrypts from the
  epoch it was welcomed at; nothing before it is readable there. Losing every
  instance loses history, and the server cannot help because it never had
  plaintext. `client.history.*` throws `NotImplementedError`.
- **Trust on first use for the first instance.** When an account has no
  active instance, whoever holds a valid Oxy token becomes the root of the
  approval chain. That window includes a user who lost or revoked every
  device. A recovery mechanism that could approve instead is designed and not
  built.
- **A revoked instance keeps the current epoch until a remaining leaf commits
  the Remove.** It no longer receives events from the server, but ciphertext
  of that epoch it obtains by other means is readable to it until then.
- **The approval chain cannot be verified from outside when an approver was
  revoked**, because another account's listing carries active instances only.
  Such an instance is refused rather than trusted.
- **No fingerprint comparison between accounts.** The chain proves an
  instance belongs to an Oxy account id; that the account is the person the
  user thinks it is remains Oxy's and the user's problem.
- **`ts-mls` is unaudited**, single-maintainer and pure TypeScript. The spike
  checked protocol behaviour, not side channels. OpenMLS and mls-rs remain to
  be compared on device.
- **Metadata and traffic analysis are not hidden**: membership, timing,
  sizes (in 256-byte steps), presence and the existence of typing traffic are
  visible to the operator.
- **Malicious JavaScript on the web origin** runs with the page's authority
  and can use the keys. CSP and Trusted Types are designed, not built.
- **No delivery receipts, no per-account typing attribution, no thumbnail
  upload, no key package pruning.** Listed with what the tree does instead in
  section 10 of the crypto page.
- **A compromised endpoint reads plaintext after decryption.** Encryption is
  end to end, not end to eye.

## Where the code is

`packages/core/src/crypto/` (engine, provider, request signing and the chain
check, at-rest cipher), `packages/core/src/sync/` and `outbox/` (epoch
gating, pending commits, the queue), `packages/backend/src/middleware/instanceAuth.ts`
and `services/platform/` (the server's half). The wire contract is
[API v1](./platform/api-v1).
